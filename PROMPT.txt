- Mapeie esse campo para a propriedade Android `totalPacotesFalhos`, usando o valor padrão zero somente quando o valor realmente estiver ausente ou nulo:

2. GOOGLE PLAY: NÃO INDICAR SUCESSO SEM VALIDAÇÃO DO BACKEND

No equivalente a GoogleBillingManager.kt, localize o fluxo de envio e tratamento da chamada POST /subscription/verify (por exemplo, enviarVerificacaoBackendV2).

O contrato atual do backend:
- Método/caminho: POST /subscription/verify
- Autenticação: cabeçalho Authorization no esquema Bearer, contendo o Firebase ID token e fornecido pelo mecanismo compartilhado do app (ApiClient/AuthInterceptor).
- JSON: `subscription_id` e `purchase_token`.
- Sucesso de validação: resposta HTTP 2xx com corpo JSON contendo `status: "success"`.
- Erro: status HTTP não 2xx, erro de autenticação/servidor, resposta inválida ou falha de rede.

Implemente o seguinte:
- Só execute `onPurchased()` e mostre mensagem de sucesso/ative o acesso premium depois de confirmar uma resposta HTTP 2xx válida e o resultado de sucesso esperado no corpo. Não converta exceções, respostas nulas ou erros HTTP em sucesso.
- Em erro HTTP ou falha de rede, informe claramente que a compra ainda não pôde ser validada pelo servidor. Não informe que a assinatura foi ativada e não libere o estado premium como se o backend tivesse confirmado.
- Mantenha o token da compra disponível para nova tentativa. Permita tentar novamente por um mecanismo compatível com o fluxo atual (ação explícita e/ou nova consulta ao BillingClient ao reabrir/retomar o app). Evite perder compras pendentes de validação após rotação, encerramento ou retorno à tela.
- Evite chamadas concorrentes/repetidas desnecessárias e mantenha o processamento na thread/contexto correto.
- Siga o tratamento de erros e a apresentação de mensagens já adotados pelo app; não descarte silenciosamente erros relevantes.
- Inspecione o fluxo de acknowledge/consume da Google Play. Não marque a assinatura como validada no backend só porque a compra foi retornada pelo BillingClient. Se o reconhecimento da compra for feito separadamente para cumprir os requisitos da Play, mantenha claramente separados os estados “compra recebida/reconhecida pela Play” e “assinatura validada/ativada pelo backend”, e preserve a possibilidade de reenviar `purchase_token` ao backend até obter confirmação. Não faça mudanças no fluxo de acknowledge sem verificar as regras e a implementação existente.
- Use o cliente compartilhado autenticado; não crie uma chamada HTTP paralela sem o Firebase ID token.

Critérios de aceite:
- HTTP 2xx com sucesso esperado: executar uma única vez o callback de sucesso e atualizar o estado premium.
- HTTP não 2xx, resposta sem sucesso válido, resposta nula ou erro de rede: não executar `onPurchased()`, não exibir sucesso e permitir nova tentativa.
- Uma falha temporária de rede não deve tornar impossível validar depois a compra ainda válida.

O app possui uma chamada planejada/usada para `PUT /atualizar-perfil`. O endpoint já está implementado no código local do backend, com autenticação Firebase e atualização do e-mail do usuário no Neon DB, mas depende de publicação na Vercel para estar disponível em produção.

- Verifique o status HTTP e o resultado da resposta. Não ignore exceções, não exiba sucesso de sincronização em caso de falha e não chame endpoint alternativo.
