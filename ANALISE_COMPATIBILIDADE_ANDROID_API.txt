ANALISE DE COMPATIBILIDADE: APP ANDROID E API ROTERIZADOR PRO
Data da revisao: 09/10/2026

ESCOPO E FONTES

Esta revisao compara:
- scan_projeto_20261009_162214.txt, snapshot textual do projeto Android;
- main.py, backend presente na raiz deste repositorio.

Esta e uma analise estatica dos contratos e trechos visiveis nesses arquivos.
O repositorio contem o backend e o snapshot textual, mas nao contem os
arquivos-fonte Kotlin editaveis do app. Nenhuma alteracao foi feita no codigo
Android, no backend ou em dependencias. Somente este relatorio foi atualizado.

RESUMO EXECUTIVO

Compatibilidades observadas:
- URL base do cliente e URL declarada pela API coincidem.
- Cadastro de usuario, consulta de status da assinatura e salvamento do
  historico usam caminhos e campos alinhados nos trechos analisados.
- Em relacao ao snapshot anterior, a verificacao de compra agora usa ApiClient
  e envia somente subscription_id e purchase_token.

Problemas ainda identificados:
1. A verificacao da compra informa sucesso e chama onPurchased mesmo se a API
   retornar erro HTTP ou a chamada falhar por rede/excecao.
2. A leitura do historico procura total_pacotes_falhos, mas a API retorna
   pacotes_falhos.
3. O fallback DELETE /excluir-historico usado pelo app nao existe na API local.
4. O app chama PUT /atualizar-perfil, rota ausente na API local, e ignora a
   resposta e excecoes da sincronizacao.
5. O valor do cabecalho Authorization esta mascarado no snapshot, impedindo
   confirmar o formato exato do token Firebase enviado.
6. A consulta de status libera em modo offline quando ocorre excecao de rede;
   e necessario confirmar se esse comportamento corresponde a regra de negocio.

DETALHAMENTO

1. URL BASE

Situacao: compativel.

O ApiClient do snapshot usa https://apiroterizadorprov2.vercel.app, mesma URL
declarada no main.py. As operacoes verificadas usam esse cliente compartilhado.

2. AUTENTICACAO FIREBASE

Situacao: o cliente compartilhado usa AuthInterceptor, mas nao e possivel
confirmar o cabecalho transmitido pelo snapshot.

A API exige Authorization no esquema Bearer com um token Firebase validado nas
rotas autenticadas. O ApiClient inclui AuthInterceptor, e a chamada de
verificacao de compra do snapshot atual passa a usar ApiClient. Entretanto, o
conteudo do cabecalho esta mascarado no snapshot; nao e possivel comprovar se o
valor enviado e "Bearer <Firebase ID token>" nem avaliar o comportamento do
cliente quando falha a obtencao do token.

Recomendacao: conferir o fonte original do AuthInterceptor e manter a
identidade do usuario derivada exclusivamente do token validado pela API, sem
aceitar firebase_uid do corpo como substituto.

3. CADASTRO DE USUARIO

Situacao: compativel nos campos e na rota.

O app chama POST /registrar-usuario e envia nome, email, cpf e android_id,
campos aceitos pelo modelo UsuarioNovo. A API associa o registro ao UID
derivado do token Firebase validado.

4. CONSULTA DO STATUS DA ASSINATURA

Situacao: contrato compativel, com ressalva sobre a regra para falhas.

O app chama GET /status-assinatura e consulta status, bloquear_app e vence_em,
campos retornados pelo backend. Estados como INATIVO, VENCIDO e VENCIDA sao
tratados como bloqueados.

No snapshot, respostas HTTP diferentes de 200 e 404 levam ao bloqueio; uma
excecao de rede, por outro lado, libera o app em "Modo Offline". Essa
liberacao pode manter acesso durante indisponibilidade ou falhas de
autenticacao. E necessario confirmar se o modo offline deve permitir acesso
sem consultar a assinatura.

5. VERIFICACAO DA COMPRA GOOGLE PLAY

Situacao: caminho e payload estao alinhados no snapshot atual; tratamento de
falhas continua incorreto.

O app e a API usam POST /subscription/verify. O snapshot atual envia a
requisicao por ApiClient com subscription_id e purchase_token, os unicos campos
do modelo PurchaseVerification. O campo firebase_uid enviado no snapshot
anterior nao aparece mais nesse trecho. A API deriva o UID do usuario do token
Firebase autenticado.

O formato exato do Authorization continua inconclusivo porque o valor foi
mascarado no snapshot.

Problema persistente no Android:
- Quando a API responde com status fora de 2xx, o app exibe "Assinatura
  ativada com sucesso!" e chama onPurchased().
- Quando ocorre uma excecao de rede, tambem exibe uma mensagem de sucesso e
  chama onPurchased().

Consequencia: a interface pode indicar que a compra foi verificada mesmo sem
confirmacao da API, causando divergencia entre o estado local e o estado
registrado no backend. O fluxo tambem reconhece a compra antes da verificacao
do backend; o trecho analisado nao evidencia tratamento de recuperacao caso a
verificacao posterior falhe.

Correcao recomendada nos fontes Android:
- Chamar onPurchased() e exibir sucesso somente apos resposta HTTP 2xx da API.
- Em erro HTTP ou de rede, comunicar estado pendente/falha e permitir nova
  tentativa ou nova consulta da compra.
- Garantir que uma compra ja reconhecida possa ser reenviada para verificacao
  sem ser tratada localmente como confirmada.

Nao se recomenda alterar a API para aceitar identidade fornecida pelo cliente
nem remover a autenticacao Firebase.

6. SALVAMENTO DO HISTORICO

Situacao: compativel nos campos examinados.

O app chama POST /salvar-historico e envia id, data_inicio_millis,
data_fim_millis, tempo_decorrido_segundos, total_paradas, pacotes_entregues,
pacotes_falhos, km_rodados, faturamento_bruto, consumo_kml e
preco_combustivel. Esses campos correspondem ao modelo RotaBackup e a rota da
API.

7. LEITURA DO HISTORICO

Situacao: incompatibilidade no nome do campo de pacotes falhos.

A API retorna pacotes_falhos. O app procura total_pacotes_falhos e usa zero
como valor padrao quando esse campo esta ausente. Assim, o historico
sincronizado pode mostrar zero pacotes falhos mesmo quando a API armazenou
outro valor.

Correcao recomendada: alterar o app para ler pacotes_falhos. Como alternativa
de compatibilidade, a API poderia incluir total_pacotes_falhos como alias, sem
remover pacotes_falhos; essa alteracao nao foi realizada.

8. EXCLUSAO DE HISTORICO

Situacao: rota principal compativel; fallback incompativel.

O app chama DELETE /deletar-historico/{rota_id}, rota existente na API. Se a
chamada falha, tenta DELETE /excluir-historico com um JSON contendo id. Essa
rota alternativa nao existe no main.py e, portanto, nao deve funcionar contra
a API local analisada.

Correcao recomendada: remover o fallback no app ou implementar na API uma
compatibilidade autenticada para essa rota, preservando a verificacao de
propriedade da rota. Nenhuma dessas alteracoes foi feita.

9. ATUALIZACAO DE E-MAIL

Situacao: rota chamada pelo app ausente na API local.

O app envia PUT /atualizar-perfil com o campo email. Essa rota nao consta no
main.py. Alem disso, o app nao verifica o codigo/corpo da resposta e descarta
silenciosamente excecoes. Portanto, o snapshot nao confirma que a alteracao
seja sincronizada com o backend.

Correcao recomendada: decidir se o banco da API deve espelhar o e-mail do
Firebase. Se sim, implementar rota autenticada que use o UID do token, valide
o e-mail e atualize o perfil; o app tambem deve verificar e comunicar o
resultado. Se nao, remover a chamada ou definir outro fluxo de sincronizacao.
Nenhuma alteracao foi feita na API nem no app.

10. CONFIGURACAO ANDROID VISIVEL NO SNAPSHOT

O snapshot informa compileSdk 36, minSdk 26, targetSdk 36 e Google Play
Billing 8.0.0. Esses valores foram registrados, mas esta comparacao trata dos
contratos entre app e API; nao houve build, teste em dispositivo ou auditoria
da compatibilidade de permissoes e APIs Android para esses SDKs.

RECOMENDACOES PRIORIZADAS

1. Corrigir o fluxo Android de verificacao da compra para nunca indicar sucesso
   sem resposta de sucesso da API e permitir recuperacao de falhas.
2. Confirmar no fonte Android o esquema Bearer enviado pelo AuthInterceptor.
3. Alinhar o leitor Android do historico ao campo pacotes_falhos ou decidir
   explicitamente por alias temporario no backend.
4. Remover o fallback de exclusao do app ou implementa-lo na API com
   autenticacao e autorizacao equivalentes a rota oficial.
5. Definir a fonte oficial do e-mail e sincronizar app/API de acordo,
   comunicando falhas no cliente.
6. Confirmar se liberar acesso em "Modo Offline" e comportamento desejado.

LIMITACOES

- A avaliacao do Android usa um snapshot textual, nao uma compilacao nem os
  arquivos Kotlin do projeto.
- O valor de Authorization foi mascarado, impedindo confirmar o token enviado.
- Nao foram realizadas chamadas reais a servicos externos, validacao de
  credenciais, acesso ao banco ou verificacao do backend publicado. O backend
  publicado pode diferir do main.py local.
- Nenhum codigo Android ou API foi modificado nesta revisao; somente este
  relatorio foi atualizado.
